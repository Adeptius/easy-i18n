# Прибрано зайві лапки для JSON-рядкових перекладів

## Проблема

Плагін зберігає внутрішнє значення перекладу (`I18nValue.raw`) як текст, що
буквально показується користувачу — у діалозі редагування (`TranslationDialog`),
у деревовидному/табличному View, а також у preview/folding прямо в коді.

Для JSON-файлів `JsonReader` раніше клав у `raw` **буквальний JSON-літерал**
значення (`JsonElement#toString()`). Для рядкових значень це означало, що
`raw` включав лапки, які Gson сам додає навколо JSON-рядка. Наслідок:

- у полі редагування рядок `"Привіт"` показувався як `"Привіт"` (з лапками) —
  щоб змінити значення, доводилось або лишати лапки, або вручну їх дописувати;
- у preview/folding в коді редактора переклад теж показувався в лапках.

Для чисел, `true`/`false`, `null` та масивів/об'єктів цієї проблеми не було —
вони й раніше показувались без лапок (їхній JSON-літерал і так без лапок).

## Що змінено

### `src/main/java/de/marhali/easyi18n/infra/json/JsonReader.java`

`readValue()` тепер розрізняє два випадки:

- **Рядок** (`JsonPrimitive.isString() == true`) — у `raw` кладеться сам
  *вміст* рядка (`element.getAsString()`), без лапок, з легким екрануванням
  контрольних символів через `I18nValue.fromUnescaped()` (той самий підхід,
  що вже використовується для YAML/Properties).
- **Все інше** (число, bool, null, масив, об'єкт) — поведінка не змінена:
  у `raw` як і раніше кладеться повний JSON-літерал (`element.toString()`).

### `src/main/java/de/marhali/easyi18n/infra/json/JsonWriter.java`

`toJsonElement()` мусить відновити правильний `JsonElement` із `raw` при
записі назад у файл. Оскільки тепер рядки в `raw` не мають лапок, а
`I18nValue` взагалі не зберігає інформацію про тип (це просто `String`),
виникає неоднозначність: текст на кшталт `[ СКРЫТЫЙ ]` або порожній рядок
`""` синтаксично збігаються з JSON-літералами масиву/`null` відповідно.

**Перша спроба фіксу** (просто пробувати розпарсити `raw` як JSON і
довіряти результату, якщо він не рядок) зламала реальні дані користувача:

| Було в файлі | Стало (баг) |
|---|---|
| `"publicProfileIsHidden": "[ СКРЫТЫЙ ]"` | `"publicProfileIsHidden": [ "СКРЫТЫЙ" ]` |
| `"BITRIX": ""` | `"BITRIX": null` |

Причина: Gson-парсер у lenient-режимі (`JsonParser.parseString`) приймає
неявні (без лапок) елементи масиву — тому `[ СКРЫТЫЙ ]` парситься як масив
з одного рядка. А для порожнього вводу Gson повертає `JsonNull.INSTANCE`
замість помилки.

**Фінальне рішення:** довіряти "не-рядковому" результату парсингу лише
тоді, коли його **повторна серіалізація (`toString()`) точно збігається**
з вихідним `raw`-текстом:

```java
JsonElement parsed = JsonParser.parseString(raw);
boolean isNonStringLiteral = !(parsed.isJsonPrimitive() && parsed.getAsJsonPrimitive().isString());
if (isNonStringLiteral && parsed.toString().equals(raw)) {
    return parsed;
}
// інакше — це звичайний рядок:
return new JsonPrimitive(value.toUnescaped());
```

Це працює надійно, бо для *справжніх* чисел/bool/null/масивів/об'єктів
`raw` — це і є прямий вивід `JsonElement#toString()` (з reader'а), тож
парсинг+серіалізація завжди дають точний round-trip. А для рядкового
тексту, який лише *схожий* на JSON-синтаксис (дужки з пробілами, порожній
рядок тощо), повторна серіалізація дає інший текст (інші пробіли/лапки,
або `"null"` замість `""`) — і такий текст коректно лишається рядком.

## Відоме обмеження

Якщо рядковий переклад **буквально** дорівнює `true`, `false`, `null` або
чистому числу (наприклад `"42"`), він все ще буде помилково прочитаний як
відповідний тип при записі — бо в такому вузькому випадку round-trip теж
збігається. Це той самий, вже прийнятий у проєкті компроміс, що й у
YAML-кодеку (`YamlReader`/`YamlWriter` мають ідентичне обмеження). На
практиці для текстів перекладів це малоймовірний кейс.

## Тестове покриття

Існуючі lossless round-trip тести
(`src/test/java/de/marhali/easyi18n/integrationTests/I18nJsonResourcesRoundtripTest.java`,
фікстури в `src/test/resources/roundtrip/json/**`) покривають рядки, числа,
bool, null, вкладені об'єкти та масиви (в т.ч. масиви з вкладеними
об'єктами як єдине leaf-значення) і мають лишитись зеленими після цієї
зміни.
